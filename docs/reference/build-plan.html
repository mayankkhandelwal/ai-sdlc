Why one plan

Seven reasons

One source of truth

Every chat and every person reads the same plan files. Nobody works from what they remember of a chat.

Safe parallel work

Dependencies are written down, so several chats can work at once without building on unfinished work.

Nothing forgotten

Every part of the architecture maps to a task. If the board doesn't list it, it doesn't happen.

Progress you can see

The board shows done, doing and ready at any moment.

"Done" means proven

Every task has done-when and proof. A fresh audit checks the proof against the plan.

Controlled change

New ideas go to the inbox first; the Lead turns them into tasks. Nothing gets built on the side.

And the seventh: the plan can change. When a spike, an audit or a live test proves something wrong, the plan and the decision records change together, in one commit.

Why live tests start early: written test briefs are cleaner than real ones, and only real use shows whether the output actually saves time. Finding that out at the pilot would be too late to change the design cheaply.

Each live test is a real task with sub-tasks, done-when and proof, followed by an audit (T-18.6) and acceptance (T-18.7). The pilot (T-17.3) and v1 acceptance (T-17.5) can't happen before them.

Live test rules

Before and after every live test

Before (task T-18.1)

  • Team or Enterprise Claude seats for anyone handling client documents (not Pro or Max)
  • The client's permission, or a non-confidential or internal project
  • Personal data and secrets removed from the brief
  • Stitch's terms checked for client data; Figma AI training turned off
  • The project is not in any test set

After

  • Write a report in docs/live-tests/: measurements, what went wrong, what to change. No client names or confidential content
  • Add failures to the failure catalog in general words only, never the client, product or domain terms (rule R1)
  • Turn changes into inbox items; the Lead plans them
  • With permission, anonymise the brief and add it as a new real test document
  • Every later agent design task reads these reports first

How the plan changes

Three ways

New work

Goes into plans/inbox.md. The Lead turns it into tasks or an epic, and the board shows them.

Something proved wrong

A spike, audit or live test shows a mistake: update the decision record and architecture in the same commit, then the affected tasks.

Dropped work

Marked skipped, with a decision record explaining why (for example, the Figma path moved to v1.1).
