Agents, one by one

14 agents and what each one does

Every agent runs through the same runner and sandbox, sends every model and tool call through the gateway, and is traced. The cards below show only what is specific to each agent. A diamond step is a decision; a red step is a human approval.

Stage 0

Ready?

Setup agent

AgentsD3

Makes a customer repo ready for agents when the readiness checker finds gaps: adds missing build, test, run and e2e scripts and the readiness section in AGENTS.md.

Runs when

Readiness report has gaps

Reads

Readiness report, build files, existing CI config

Writes

Pull request with scripts + readiness section

May use

Read/write files in its pod, run commands, push its own branch

Model

Default

Hands off to

Readiness checker (re-check)

  1. Read the gap list from the readiness report
  2. Detect the stack from build files pom.xml · package.json · *.csproj
  3. Look at existing CI config to reuse the commands the team already runs
  4. Write the missing scripts and the readiness section
  5. Run each command in the pod
  6. All commands pass?No: fix and run again, up to 3 tries, then report to a human
  7. Open a pull request for the customer's team to approve
  8. Trigger the readiness checker again

If it fails: the project stays blocked and the report lists what a human must add.

Stage 1

Understand

Requirement agent

Agents

Turns rough input (a ticket, a document, meeting notes) into one clear, structured requirement, and asks humans about anything unclear instead of guessing.

Runs when

New ticket or document arrives, and readiness passed

Reads

Ticket, attachments, existing features from the knowledge layer, project memory

Writes

Requirement record: goal, users, scope in/out, non-functional needs, open questions

May use

Knowledge search (read-only), Jira via MCP (read + comment). No code access.

Model

Default

Hands off to

BA agent

  1. Receive the ticket event from the orchestrator
  2. Guardrail check: scan ticket text and attachments for injected instructions
  3. Search the knowledge layer for related features and past decisions
  4. Extract goal, users, in scope, out of scope
  5. List gaps and conflicts with existing behaviour
  6. Any blocking questions?Yes: post them on Jira and the dashboard, set state to needs_input, wait; resume when answered
  7. Add non-functional needs: performance, security, data rules
  8. Output valid against the requirement schema?No: regenerate with the validation errors, up to 2 times
  9. Save the requirement and hand off to the BA agent

If it fails: the requirement stays in needs_input; it never moves forward on guesses.

BA agent

Agents⏸ Requirement approvalD9

Writes the user stories and acceptance criteria, and lists the user journeys that will later be tested end to end. This defines "done" for everything that follows.

Runs when

Requirement record is saved

Reads

Requirement record, existing user journeys

Writes

User stories, Given/When/Then criteria, user journeys, trace IDs

May use

Knowledge search (read-only). No code access.

Model

Default

Hands off to

Requirement approval, then Architecture agent

  1. Read the requirement
  2. Identify user roles and the journeys each role takes
  3. Write one user story per journey step As a … I want … so that …
  4. Write acceptance criteria for each story Given … When … Then …
  5. Give every requirement line and story a trace ID
  6. Every requirement line covered by a story?No: add the missing stories and check again
  7. Mark which journeys the Journey QA agent must test
  8. ⏸ Requirement approval (requirement + stories together)
  9. Hand off to the Architecture agent

If it fails: the reviewer's comments go back to this agent; it revises and asks again.

Design

Architecture agent

Agents

Decides where the change lives in the system and defines the contracts first (API, data model, events), so parallel build agents all build against the same agreement.

Runs when

Requirement approved

Reads

Stories, code map, existing ADRs and conventions, readiness report (stack)

Writes

Design note, OpenAPI contracts, data model changes, new ADRs

May use

Knowledge search, read repo; write only to a design branch

Model

Stronger model (high-stakes step)

Hands off to

Planner agent

  1. Load the architecture map: modules, services, call graph
  2. Load existing ADRs and coding conventions
  3. Decide which modules or services change
  4. Design data model changes: tables, fields, indexes
  5. Write API contracts as OpenAPI, plus event formats if needed
  6. Check the design against non-functional needs: security, performance, data rules
  7. Conflicts with an existing ADR?Yes: write a new ADR proposal and flag it for the plan approval
  8. Write the design note and ADRs into project memory
  9. Hand off to the Planner agent

If it fails: a contract that doesn't validate (bad OpenAPI) is regenerated; an unresolvable conflict goes to a human.

Planner agent

Agents⏸ Plan approvalD9

Turns stories and design into a story graph: small technical stories in a safe order, each assigned to one build agent. This is what makes advanced projects possible.

Runs when

Design note and contracts saved

Reads

Stories, design note, contracts, past run history (size and cost)

Writes

Story graph: stories, dependencies, size, agent type, contracts, trace IDs, cost estimate

May use

Knowledge search (read-only)

Model

Stronger model

Hands off to

Plan approval, then Orchestrator

  1. Turn each user story plus the design into technical stories
  2. Put contract stories first: API spec, database migration
  3. Estimate the size of each story
  4. Too big for one agent run?Yes: split it and estimate again
  5. Assign an agent type: backend, frontend, or infra + DB
  6. Set dependencies between stories
  7. Graph valid: no loops, every acceptance criterion covered?No: fix the graph and validate again
  8. Estimate total time and cost from past runs
  9. ⏸ Plan approval
  10. Hand the graph to the orchestrator

If it fails: validation errors are fixed before any human sees the plan; reviewer comments come back here.

Build

D5 D8

Backend agent

Agents

Implements one backend story (API endpoints, business logic, data access) with tests, inside its own sandbox pod, and opens a pull request.

Runs when

Orchestrator starts a ready backend story

Reads

Story, OpenAPI contract, relevant code, project memory, readiness commands

Writes

Commits on its branch, tests, pull request, memory notes

May use

Files and commands inside its pod only; no internet except package registries; push via a scoped token held outside the pod

Model

Default; stronger model after 3 failed tries

Hands off to

QA, Security and Code review agents

  1. Pod starts with the repo at main and a new story branch
  2. Load the story, contract and project memory
  3. Search the knowledge layer for the files that matter, using an explorer sub-agent
  4. Write a short plan of the change
  5. Write failing tests from the acceptance criteria
  6. Implement the code
  7. Run build and tests with the readiness commands
  8. All green?No: read the errors, fix, go back to step 7, up to 10 rounds
  9. Matches the OpenAPI contract and every acceptance criterion?No: fix and go back to step 7
  10. Commit, push, open the pull request with a structured description
  11. Write decisions and learnings to project memory
  12. Pod is deleted

If it fails: it ends with a report of what it tried; the orchestrator retries, switches model, or escalates.

Frontend agent

Agents

Implements one frontend story (screens, components, API calls) with tests, and attaches screenshots of what it built so reviewers can see it.

Runs when

Orchestrator starts a ready frontend story

Reads

Story, OpenAPI contract, UI conventions, existing components, project memory

Writes

Commits, component tests, screenshots, pull request

May use

Same pod rules as the Backend agent, plus a headless browser inside the pod

Model

Default; stronger model after 3 failed tries

Hands off to

QA, Security and Code review agents

  1. Pod starts with the repo and a new story branch
  2. Load the story, API contract, UI conventions and memory
  3. Find existing components to reuse
  4. Generate or refresh the typed API client from the OpenAPI contract
  5. Write component tests from the acceptance criteria
  6. Build the screens and components
  7. Run lint, type check and tests
  8. All green?No: fix and go back to step 7, up to 10 rounds
  9. Start the app in the pod and screenshot the changed screens
  10. Run an accessibility check on those screens
  11. Commit, push, open the pull request with screenshots
  12. Write memory notes; pod is deleted

If it fails: same as Backend: report, then retry, model switch, or escalation.

Infra + DB agent

Agents

Handles database migrations, configuration, Dockerfiles and pipeline files for the customer's app. It never applies anything to a real environment, and risky changes always go to a human.

Runs when

Orchestrator starts a ready infra or database story

Reads

Story, data model design, existing migrations and infra files

Writes

Migration (forward + rollback), infra files, pull request with a migration plan

May use

Pod with a throwaway database; validation tools only (plan, lint), never apply

Model

Default; stronger model after 3 failed tries

Hands off to

QA, Security and Code review agents

  1. Pod starts with the repo and a throwaway database
  2. Load the story and the data model design
  3. Write the forward migration and its rollback
  4. Run forward, then rollback, then forward again on the throwaway database
  5. Can this lose or lock data?Yes: mark the pull request "human review required" with the reason
  6. Update infra files: config, Dockerfile, pipeline
  7. Validate without applying terraform plan · helm lint · docker build
  8. Open the pull request with the migration plan; pod is deleted

If it fails: a failed rollback test blocks the story; it never reaches the gates.

Stage 5

Check

⏸ Merge: always humanD9 D14

These three agents run at the same time on every pull request. The orchestrator combines their reports: all pass → merge approval; any blocking finding → feedback to the build agent (one retry used).

QA agent

Agents

Checks that every acceptance criterion has a real test, that all tests pass in a clean environment, and that nothing else broke.

Runs when

Pull request opened or updated

Reads

Diff, story, acceptance criteria, test results

Writes

QA report: criteria → tests, missing tests, results, coverage change

May use

Read repo, run tests in a fresh pod, comment on the pull request

Model

Default

Hands off to

Orchestrator (gate result)

  1. Map each acceptance criterion to the tests in the pull request
  2. Any criterion without a test?Yes: blocking finding
  3. Judge whether each test really checks its criterion, not just runs
  4. Run the full test suite in a fresh pod
  5. Any failure?Yes: re-run once; fails twice = real failure, passes = mark as flaky
  6. Compare coverage with main
  7. Write the structured QA report and post a summary comment
TopicsTest coverageFlaky testsTraceabilityStructured outputLLM-as-judge

Security agent

Agents

Runs the security scanners, separates real problems from false alarms, and reviews access and permission logic. Critical findings block the merge, and no agent can override them.

Runs when

Pull request opened or updated

Reads

Diff, scanner results, requirement's security needs

Writes

Security report: findings, real or false alarm, severity, fix hints

May use

Read repo, run scanners in a pod, comment on the pull request

Model

Default

Hands off to

Orchestrator (gate result)

  1. Run Semgrep (code), Trivy (dependencies) and Gitleaks (secrets)
  2. Collect all findings in one list
  3. For each finding, decide real or false alarm, with a written reason
  4. Review authentication and permission logic in the diff who can see or change what
  5. Check against the requirement's security needs and common web risks
  6. Set severity for each real finding
  7. Any critical finding?Yes: block the merge; only a human can clear it
  8. Write the security report with a fix hint per finding

Orchestrator → human merge approval

  2. Check correctness against each acceptance criterion
  3. Check that the code matches the API contract
  4. Check design and conventions against the ADRs
  5. Check readability, duplication and error handling
  6. Label each comment blocking or suggestion
  7. Post inline comments
  8. QA, Security and Review all pass?No: orchestrator sends all blocking findings to the build agent

Agentsenvironment: Platform

Reads

Writes

May use

Default

Hands off to

Orchestrator (fix stories) or Release agent

  1. Ask the platform for a temporary environment: full app plus seeded test data
  2. Load the module's user journeys
  3. Write or update Playwright journey tests
  4. Run all journeys and record each one

Platform parts, one by one

9 parts the agents run on

These are not agents. They are the software the three of you build (or wire in) so the agents can run safely, for weeks, inside a customer's cloud.

Readiness checker

PlatformD3 D4

Confirms a machine can build, test and run the customer's repo without a human, before any agent starts.

  1. Clone the repo into a fresh pod
  2. Read the readiness section build · test · run · e2e · lint
  3. Run each command with time and memory limits; record result and duration
  4. Detect the stack
  5. Certified stack?Yes: mark certified · No: mark best-effort
  6. Write the readiness report to the dashboard
  7. Any gaps?Yes: start the Setup agent, then check again · No: project is ready
TopicsAgent readinessReproducible buildsKubernetes pod

Orchestrator

PlatformD7 D9

Runs the story graph for days or weeks and never loses its place. Every step is saved in Postgres, so after a crash it continues from the last finished step.

  1. Receive the approved story graph and the project's approval policy
  2. Find ready stories: all their dependencies merged
  3. Start up to N stories at once, within budget
  4. For each story: create the branch, call the runner with the right build agent
  5. Wait for the pull request and the three gate reports (GitHub webhooks)
  6. Gates pass?No: send findings back · try 4 → stronger model · after that → human
  7. ⏸ Sleep until merge approval arrives from the dashboard
  8. Last story of a module merged?Yes: start the Journey QA agent; fix stories it creates go back to step 2
  9. All modules verified?Yes: start the Release agent

queued → running → in_gates → changes_needed ↺ → awaiting_merge → merged · or escalated / failed

Must pass: a 2-week test run with a forced crash in the middle. If DBOS loses work, switch to Temporal.

TopicsDurable executionDBOSTemporalState machineIdempotencyRetries with backoffWebhooksMulti agent system

Runner + sandbox

PlatformD5 D8

Starts any agent safely. Everything goes through one function, runAgent(agent, task), so the agent SDK or model can be swapped later without touching the rest.

  1. Receive runAgent(agent, task) from the orchestrator
  2. Load the agent definition: instructions, tools, MCP servers, model
  3. Create a Kubernetes pod with CPU, memory and time limits
  4. Enterprise isolation switched on?Yes: run the pod under gVisor or Kata
  5. Apply the network policy: package registries and model endpoint only
  6. Start the Claude Agent SDK with the definition; model calls go through the gateway
  7. Stream every step to tracing
  8. Collect the result; push the branch with a scoped token held outside the pod
  9. Delete the pod and return the result
TopicsAgent harnessClaude Agent SDKHooks and permissionsCloud agentKubernetesgVisor / KataNetwork policyAdapter pattern

Knowledge layer + project memory

Agents

Lets agents find the right code in a big repo without reading all of it, and remember decisions across weeks. This is what keeps story 200 as correct as story 1.

  1. On every merge, receive the list of changed files
  2. Parse them with tree-sitter: files, classes, functions, who calls what
  3. Update the code map and call graph
  4. Split code into chunks and create embeddings
  5. Store embeddings in Postgres (pgvector), so no extra database is needed
  6. Store project memory: decisions, conventions, progress, ADRs
  7. Serve one search API to agents: keyword + meaning + call graph
TopicsRAGCode indexing (AST, tree-sitter)EmbeddingsVector search (pgvector)Hybrid searchContext engineeringAgent memory

Gateway + policy

PlatformProductD5 D9

The single checkpoint for every model call and tool call: is it allowed, is it within budget, and is it recorded?

  1. Receive a model or tool call, tagged with agent, story and project
  2. Tool allowed for this agent?No: block and log
  3. Budget left for this story and project?No: pause the story and alert a human
  4. Input guardrail: check for injected instructions
  5. Choose the model: default, or stronger if escalated
  6. Send to the customer's cloud model endpoint Bedrock · Vertex · Foundry
  7. Output guardrail; record tokens, cost and time
  8. Return the result
TopicsLLM gatewayModel routingGuardrailsPrompt injection protectionRBACRate limits and budgets

Traces + audit

ProductD14

Shows what every agent did, what it cost and where it failed; keeps a tamper-proof record of every human approval.

  1. Every agent run becomes a trace in Langfuse: steps, tool calls, tokens, time
  2. Link each trace to its story, project and pull request
  3. Roll up cost and time per story, module and project
  4. Alert on failures, loops and cost spikes
  5. Write every approval to an append-only audit log: who, when, what they saw
TopicsAgent tracingLLM observabilityOpenTelemetryLangfuseAudit logs

Evaluation

AgentsD4 D6 D12

Measures whether the agents are actually good, every week and before any change to a prompt or model. Written in Python.

  1. Keep a fixed set of real tasks for each certified stack
  2. Run every task through the full flow in sandboxes
  3. Score each run: tests pass, gates pass, LLM judge, human-change rate
  4. Compare with the previous agent version
  5. Worse than before?Yes: the prompt or model change is not released
  6. Publish the weekly numbers against the launch targets

Install package

ProductD2 D14

One Helm chart that installs everything in a customer's cloud, or as a copy you host for an agency.

  1. Customer runs the Helm install in their Kubernetes cluster
  2. Chart installs platform services, Postgres, Keycloak and Langfuse
  3. Customer sets the model provider: Bedrock, Vertex or Foundry
  4. Customer connects GitHub and Jira, and their SSO
