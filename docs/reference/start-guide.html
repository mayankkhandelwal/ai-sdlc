What we build

One document in, an approved design out

A Claude Code plugin with several AI agents. A user gives one project brief; the agents turn it into a clear requirement, user stories, a screen list and a full UI design in Google Stitch or Figma. People answer questions and approve at each important step.

Read document→ Requirement + questions→ Stories + screen list→ You approve→ Style + screen messages→ 1–2 sample screens→ Feedback or "Go"→ Full UI

The full design is in docs/architecture/ (the master) and docs/mvp-flow.md. We haven't written product code yet; we've built the system to build it safely.

How memory works

Why a new chat still knows everything

The problem

  • A chat forgets everything when it ends
  • A long chat gets worse: it forgets early rules and mixes up details ("context rot")
  • So chats must be short, and the knowledge must live somewhere else

The fix: files are the memory

  • CLAUDE.md is read automatically by every chat
  • The task file says exactly which few files to read, never "everything"
  • Each chat ends by writing its handoff and committing
  • Decisions go into ADR files; nothing is decided "in chat only"
A new chat readsWhy
CLAUDE.mdAutomatically: what the project is, the rules, where things are
plans/handoff/latest.mdThe overall state, written by the Lead
plans/tasks/T-xx.y-….mdIts one task: goal, files to read, sub-tasks, done-when
plans/handoff/T-xx.y.mdIf the task was started before: where that chat stopped
The files the task listsUsually one or two architecture sections. Nothing else
A task's life

From "todo" to "done"

todo

Waiting. It becomes ready when everything it depends on is done.

doing

A Builder chat works on it in its own folder and records proof.

review

Builder finished; commits on its branch; writes its handoff.

audit

A fresh Auditor chat checks every "done when" against the proof. It never fixes.

done

Audit PASS. The Lead merges the branch into main.

RoleWhoDoes
LeadOne chat in the main repo folderPicks ready tasks, merges after PASS audits, sorts new work from plans/inbox.md, keeps the roadmap. Never writes product code
BuilderOne chat per task, in that task's own folderDoes one task, records proof, writes its handoff
AuditorA new chat, never the builder'sChecks proof, reruns tests, writes PASS or FAIL
YouYou and the teamAccounts and keys, answer-key reviews, approvals, accepting finished epics

This works: the plan system itself needed 8 audits before it passed, and each failed audit found real problems that were then fixed.

Many chats at once

Running several chats at the same time

Yes: run several task chats in parallel. Each one gets its own folder (a git worktree) and its own branch, so they never touch each other's files.

D:\AI-Job\
  AI_SDLC\              ← main repo. The LEAD chat runs here. main branch.
  AI_SDLC-t-02-2\       ← worktree for task T-02.2. Builder chat #1. Branch t-02-2-...
  AI_SDLC-t-02-4\       ← worktree for task T-02.4. Builder chat #2. Branch t-02-4-...
  AI_SDLC-t-02-7\       ← worktree for task T-02.7. Builder chat #3. Branch t-02-7-...
  (hold-out folder)     ← outside the repo. No chat opens it.

Rules for parallel chats

  • One task per chat; one chat per task
  • Each Builder writes only: its task file, its own handoff plans/handoff/T-xx.y.md, and the files its task produces
  • Only the Lead edits plans/roadmap.md and plans/handoff/latest.md, and merges
  • Keep worktrees next to the repo, as above

How many at once

  • Start with 3 Builder chats + 1 Lead chat
  • All chats share the same Claude subscription's usage, so more chats use it up faster. Max plan recommended
  • Only start tasks the board lists as ready

Audit each finished chat

Claude · fresh session

When a Builder chat finishes, close it. Open a new session in the same task folder and paste this (change the task ID):

Paste in a new session, same folder
You are the Auditor for T-02.2. Read plans/audits/README.md and plans/tasks/T-02.2-spike-guard-hook-identity-and-fail-closed.md. Check every done-when item against the proof, rerun the tests and the generality check, and write plans/audits/T-02.2.md with PASS or FAIL. Don't fix anything. Commit the audit file on this branch.
