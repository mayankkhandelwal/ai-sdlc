What we build

One document in, an approved design out

A Claude Code plugin with several AI agents. A user gives one project brief; the agents turn it into a clear requirement, user stories, a screen list and a full UI design in Google Stitch or Figma. People answer questions and approve at each important step.

Read document→ Requirement + questions→ Stories + screen list→ You approve→ Style + screen messages→ 1–2 sample screens→ Feedback or "Go"→ Full UI

The full design is in docs/architecture/ (the master) and docs/mvp-flow.md. We haven't written product code yet; we've built the system to build it safely.

How memory works

Why a new chat still knows everything

The problem

  • A chat forgets everything when it ends
  • A long chat gets worse: it forgets early rules and mixes up details ("context rot")
  • So chats must be short, and the knowledge must live somewhere else

The fix: files are the memory

  • CLAUDE.md is read automatically by every chat
  • The task file says exactly which few files to read, never "everything"
  • Each chat ends by writing its handoff and committing
  • Decisions go into ADR files; nothing is decided "in chat only"

A task's life

From "todo" to "done"

todo

Waiting. It becomes ready when everything it depends on is done.

doing

A /next chat builds it on its own branch and records proof.

review

Build finished, committed, handoff written.

audit

A checker sub-agent with fresh context checks every "done when". It never fixes.

done

PASS. The same chat merges the branch into main and updates the handoff.

RoleWhoDoes
LeadThe end of each /next chatMerges after PASS, updates the roadmap and the handoff. A separate Lead chat only when the plan itself changes. Never writes product code
BuilderA new /next chat for each taskDoes one task, records proof, writes its handoff
AuditorA sub-agent the chat starts, with fresh contextChecks proof, reruns tests, writes PASS or FAIL
YouYou and the teamAccounts and keys, answer-key reviews, approvals, accepting finished epics

This works: the plan system itself needed 8 audits before it passed, and each failed audit found real problems that were then fixed.

One chat per task

Type /next. That's the whole method

One chat does one whole task: it picks the task, plans, builds, gets an independent check, and merges. You approve its plan and answer its questions. Then you open a new chat for the next task.

  New chat in D:\AI-Job\AI_SDLC  →  type  /next
        │
        ├─ 1. picks the next ready task, reads only what it needs
        ├─ 2. shows its plan  ──────────────────────────  you say "go"
        ├─ 3. builds it, records proof, commits on the task branch
        ├─ 4. starts a CHECKER sub-agent (fresh context)  →  PASS or FAIL
        │        FAIL → fixes → checks again (asks you after 3 fails)
        ├─ 5. PASS → merges into main, updates roadmap + handoff
        └─ 6. asks you before pushing to GitHub  →  "open a new chat, type /next"

Every chat, every time

  • Folder: D:\AI-Job\AI_SDLC
  • The app's worktree box: unticked
  • Type /next; name the chat after its task (T-02.2)
  • When it's merged, close it and open a new one

Why one chat per task

  • A new chat starts small and sharp: it reads only about 2,500 tokens to know the project
  • No copy-paste and no switching windows: the checker runs inside the chat
  • The checker still has fresh context, so it's independent
  • With 2–3 people: /next agents, /next platform, /next product, each on their own computer
