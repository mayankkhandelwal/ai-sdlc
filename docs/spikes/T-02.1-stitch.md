## Commands run

```text
npm init -y; npm i @google/stitch-sdk            # 19 s, 0 vulnerabilities
npm pkg set type=module
node spike.ts      # run by the project lead; writes out/results.json + HTML/PNG files
node resume.ts     # run by the project lead 21 min later; writes out/resume.json; no generation
```

What `spike.ts` does: reads the key from Windows Credential Manager → `new StitchToolClient({ apiKey })` →
`list_tools`, `list_projects`, `create_project` → `generate` 3 screens (DESKTOP) from 3 general sample messages
(sign-in, list with filters, create-record form) → downloads HTML and PNG of each → edits the form ("add a required
Category dropdown under Title; make Save primary") → `getScreen` by ID → `list_screens`. Every result is passed
through a scrub that replaces the key with `[KEY]` before writing. stderr of the keychain call is dropped.

## Findings (general, not about one document)

1. **Stitch rewrites what it is told.** Asked for fields Title, Owner and buttons Save, Cancel, it produced
   "Record Name", "Record Owner", "Create Record", "Save as Draft", invented a product name and domain, and added
   side panels and a checkbox. The edit did add Category in the right place. → The screen check (ADR-13) and
   strict screen messages (ADR-09) are needed; field names must be compared after parsing, never trusted.
2. **No read-back, no job ID.** `generate` is one blocking call (~1 min) that returns the screen; there is no job
   ID before it finishes, and the screen cannot be listed or fetched later. A crash or timeout mid-call loses the
   screen and its quota. → ADR-25 "job IDs saved before waiting; resume always works" cannot hold for Stitch as
   is. The adapter must save HTML and image from the response at once, and `resume(job)` can only re-run.
3. **An edit is a new screen.** Fits "every file versioned" (ADR-25): keep both IDs.
4. **No quota API.** Quota per screen can only be counted by the script itself (1 generation per call) and
   checked by hand on the website.
5. **Exported HTML pulls from CDNs** (Tailwind, Google Fonts). The facts parser must parse it, never run it
   (3.5 "parsed, never run" holds).
6. **Keychain read is Windows-only in this spike.** macOS (`security`) and Linux (`secret-tool`) still need the
   same small reader; a Node keychain library was not tried.

## ADR-11

**Confirmed, with one change for T-02.8:** SDK + keychain + one script works, and plugin secrets do not reach
Bash, so the script must read the keychain itself. Not proven: "resumable" (finding 2). The SDK is not an officially
supported Google product (finding, question 2).

## For T-02.8 (affected ADRs and sections)

- **ADR-11:** keep; reword "official SDK" to "Google Labs SDK (not officially supported)"; drop "resumable"
  from its consequences or add how.
- **ADR-25:** Stitch gives no job ID and no read-back; decide the Stitch resume rule (re-run and count quota).
- **3.6 design adapter:** `resume(job)` for Stitch = re-run; `edit` returns a new screen version.
- **3.7:** keychain reader needed on macOS and Linux too.
- **ADR-13 / ADR-09:** finding 1 is the evidence that field names drift.
- **Agent-calls-MCP path (rejected in ADR-11):** same endpoint and same 15 tools; it would add no read-back or quota.
  A plugin MCP server could take the key from a sensitive `userConfig` header, so the key would also stay in the
  keychain on that path. The reasons to keep the script stay: exact, countable calls and no HTML in the context.
