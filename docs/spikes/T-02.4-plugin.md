## Answers

| # | Question | Answer | Proof |
|---|---|---|---|
| 1 | What name does a plugin command get? | **Always `<plugin>:<command>`.** Plugin `mvp` with `commands/start.md` and `commands/mvp.md` registers `mvp:start` and `mvp:mvp`. The agent `agents/reader.md` registers as `mvp:reader` | Run `init` (slash command list) |
| 2 | Can the user type the short name? | **No (headless).** `/mvp:start brief.pdf` → `START-OK brief.pdf`; `/mvp:mvp` → `MVP-OK`. `/start brief.pdf` was not a command (the model treated it as text and went looking for the file); `/mvp` was not a command ("isn't available … use `/mvp:mvp` or `/mvp:start`"). So the 2.11 table must use `/mvp:<verb>`; a bare `/mvp` is impossible, the nearest is `/mvp:mvp` or a verb such as `/mvp:next` | Runs `cmd1`–`cmd4` |
| 3 | Is the plugin's `bin/` folder on PATH? | **Yes for the Bash tool, no for the PowerShell tool (Windows).** Bash PATH holds `…/plug/mvp/bin`; `which hello` finds it. PowerShell: `hello` not recognised, PATH has no plugin entry | Runs `bin`, `bin2` |
| 4 | Does a Python bin script run on Windows? | **Yes, through a bash wrapper with no extension** (`bin/hello` → `exec <python> bin/hello.py`). Running `hello.py` by name **fails**: its `#!/usr/bin/env python3` shebang hits the Windows Store stub `python3` (exit 49, "Python was not found"). The wrapper must probe for a real Python: `py -3`, then `python3`, then `python`, each checked with `-c` for ≥ 3.11 | Runs `bin`, `bin2`, `probe` |
| 5 | Can the script find the plugin folder? | **Not by env var inside tools.** `CLAUDE_PLUGIN_ROOT` is empty in Bash tool calls and in `!` command lines. It **is** set for hooks (env) and is **substituted as text** in command files (`${CLAUDE_PLUGIN_ROOT}` → `C:/Users/…/plug/mvp`, forward slashes). A bin script finds its own folder from `$0` / `__file__` | Runs `bin2`, `probe`, `bg` hook log |
| 6 | Can a command run a bin script itself before the model sees it? | **Yes.** A `!`hello from-command`` line in `commands/probe.md` (with `allowed-tools: Bash(hello:*)`) ran in bash and its output was pasted into the prompt. Good for deterministic steps (e.g. `mvp-state status`) without spending a model turn | Run `probe` (transcript) |
| 7 | How does the main session wait for a background agent? | **It does not block; it is told.** `Agent` with `run_in_background: true` returns at once ("Async agent launched … You will be notified automatically when it completes"). The main session went on (said `WAITING`, first `result`: 3 turns, 9.9 s); when the agent finished, the session got a new turn with the agent's report (second `result`: 1 turn, 4.0 s). In `claude -p` the process stays alive until the background agent ends and prints **two** `result` events, so a caller must read the last one | Run `bg` |
| 8 | Does `tools:` limit an agent to exact tools? | **Yes for tool names.** `mvp:reader` with `tools: Read` listed only `Read`; asked to run `echo BASH-RAN` and write `c.txt`, it said it had no such tools; the hook log shows only `Read` calls from it and `c.txt` was not created | Run `bg` |
| 9 | Does `tools: Bash(hello:*)` limit an agent to one command? | **No.** The pattern only exposes the **whole Bash tool**; it is not an allow rule. With no allow rule even `hello` asked for approval (headless = refused). With the session allow rule `Bash(hello:*)`, `hello` ran, `echo … > d.txt` needed approval (refused), but **`ls` ran with no rule**: Claude Code lets read-only commands through by itself. "Only our scripts" therefore needs the **guard hook** to deny any Bash command that is not a plugin bin script | Runs `runner`, `runner2` |
| 10 | Do hooks shipped in the plugin (`hooks/hooks.json`) behave like project hooks? | **Yes.** Same fields: agent calls carry `agent_type` + `agent_id`, main calls carry neither. **`agent_type` is namespaced: `mvp:reader`**, not `reader`. `CLAUDE_PLUGIN_ROOT` is set in the hook's env and `${CLAUDE_PLUGIN_ROOT}` is expanded in the hook command | Run `bg` (hook log, table A) |
| 11 | Does `\|\| exit 2` keep a plugin hook fail-closed? | **Yes.** Guard raising an exception with `python guard.py \|\| exit 2`: both the main `Read` and the `Agent` start were blocked ("hook error … This hook comes from the mvp@inline plugin") | Run `crash` |
| 12 | Can a plugin hook deny one agent only? | **Yes.** Rule "deny `Read` when `agent_type` ends with `reader`": main read `a.txt` (apple); `mvp:reader` got `GUARD: reader may not Read` | Run `deny-reader` |
| 13 | Does Claude's Read tool need poppler for PDF page ranges? | **Yes.** Without poppler: `pages: "5-7"` → "pdftoppm is not installed. Install poppler-utils …". A whole small PDF (no `pages`) still read fine (sent as a document, all 12 markers) | Runs `pdfread`, `pdfread-whole` |
| 14 | Do page-range reads work with poppler on Windows? | **Yes.** Read `pages: "5-7"` → 3 page images, markers 05–07. `pages: "11-14"` on a 12-page file → 2 pages, **no error** (range cut silently). Script side: `pdftotext -f 5 -l 7` → markers 05–07 in 0.10 s; `pdftoppm -f 5 -l 7 -r 100 -png` → 3 PNGs in 0.6 s, text drawn correctly despite "No display font for 'Symbol'" warnings on stderr | Runs `pdfread2`, `pdfread3`, shell |
| 15 | Any Windows trap with poppler? | **Yes, two.** (a) Git for Windows ships **Xpdf** `pdftotext` 4.00 in `/mingw64/bin`, which comes **before** the user PATH in Git Bash, so `pdftotext` is the wrong program even after poppler is installed (`pdftoppm`/`pdfinfo` are fine: Xpdf has none). Scripts must find poppler by checking `pdftoppm -v` / `pdftotext -v` says a poppler version, or call it from the folder where `pdftoppm` lives. (b) winget adds poppler to the user PATH only for **new** sessions; a running Claude Code keeps the old PATH | `which -a`, `-v` outputs |
| 16 | macOS and Linux (bin scripts, poppler) | **Not proven.** Expected: bin on PATH, shebang `python3` works, poppler from `brew`/`apt` (the Read error text names these). Needs one run on each before the plugin ships to testers | — |

## The spike plugin

```text
plug/mvp/.claude-plugin/plugin.json   {"name": "mvp", "version": "0.0.1", "description": "..."}
plug/mvp/commands/start.md            Reply with exactly: START-OK $ARGUMENTS
plug/mvp/commands/mvp.md              Reply with exactly: MVP-OK
plug/mvp/commands/probe.md            ${CLAUDE_PLUGIN_ROOT} line + !`hello from-command`; allowed-tools: Bash(hello:*)
plug/mvp/agents/reader.md             tools: Read, model: haiku
plug/mvp/agents/runner.md             tools: Bash(hello:*), model: haiku
plug/mvp/bin/hello.py                 prints platform, Python version, argv, CLAUDE_PLUGIN_ROOT
plug/mvp/bin/hello                    bash wrapper, below
plug/mvp/hooks/hooks.json             PreToolUse ".*": log.py, then guard.py || exit 2 (timeout 10)
plug/mvp/hooks/log.py                 appends the hook input + CLAUDE_PLUGIN_ROOT to $SPIKE_LOG (one file per run)
plug/mvp/hooks/guard.py               SPIKE_GUARD = allow | crash | deny-reader
```

Working wrapper (`bin/hello`):

```bash
#!/usr/bin/env bash
here="$(cd "$(dirname "$0")" && pwd)"
for c in "py -3" python3 python; do
  if $c -c "import sys; sys.exit(0 if sys.version_info >= (3, 11) else 1)" >/dev/null 2>&1; then
    exec $c "$here/hello.py" "$@"
  fi
done
echo "mvp: Python 3.11+ not found (tried py -3, python3, python)" >&2; exit 127
```

Hook command: `python "${CLAUDE_PLUGIN_ROOT}/hooks/guard.py" || exit 2`. `claude plugin validate plug/mvp` passed
(one warning: no author).

## What this changes (for T-02.8)

- **2.11 Project commands:** every command becomes `/mvp:<verb>`. `/mvp` alone cannot exist; pick
  `/mvp:next` (or `/mvp:mvp`) for "continue". Commands such as `/mvp:status` can use a `!` line to run
  `mvp-state status` with no model turn
- **3.7 What runs where / ADR-16 (Python scripts) / ADR-01 (plugin):** scripts ship as extension-less bash
  wrappers in `bin/` + `.py` files; the wrapper probes `py -3`, `python3`, `python` for ≥ 3.11. Agents call
  scripts with the **Bash** tool (PowerShell does not see `bin/`). Scripts find their files from `__file__`,
  not `CLAUDE_PLUGIN_ROOT`. Poppler is a real install step on Windows (winget package above) and a new Claude
  Code session is needed after it; scripts must reject Xpdf's `pdftotext` from Git for Windows
- **ADR-04 (a script reads documents):** page-range reads work both ways on Windows (`pdftotext -f/-l` in the
  script; Read `pages` for the AI's look at a page). Read cuts an out-of-range request silently, so the script,
  not the AI, must check page numbers against `pdfinfo`
- **3.5 permission matrix / ADR-19:** `tools:` gives exact **tools**, not exact **commands**. Any agent with
  Bash can run read-only commands with no approval. The guard hook must deny Bash calls from agents unless the
  command is one of the plugin's bin scripts. Guard rules must match **namespaced** agent names (`mvp:<agent>`).
  Plugin-shipped hooks fail closed with `|| exit 2` the same way as project hooks (T-02.2 result holds)
- **Background agents (2.x orchestration):** the main session is notified, it does not wait in a call; in
  headless runs read the **last** `result` event
- **Open:** repeat answers 3, 4, 13–16 on macOS and Linux before testers outside Windows get the plugin
